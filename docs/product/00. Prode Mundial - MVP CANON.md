# **Prode Mundial \- MVP CANON.md**

## **1\. Propósito del documento**

Este documento define la **verdad oficial del MVP** de Prode Mundial.

Su objetivo es:

* eliminar contradicciones entre documentos  
* congelar decisiones clave de producto y arquitectura  
* definir qué documentos mandan en caso de conflicto  
* servir como referencia base para Codex durante toda la implementación

---

## **2\. Principio rector**

**El MVP prioriza simplicidad, claridad y ejecución robusta por sobre completitud funcional.**

Todo lo que no contribuya directamente a:

* predicción rápida  
* scoring claro  
* competencia social en ligas  
* retorno diario

queda fuera del MVP.

---

## **3\. Decisiones oficiales del MVP (binding)**

### **3.1 Competencia**

El MVP **NO incluye ranking global**.

La competencia visible se limita a:

* rankings por liga  
* posición del usuario dentro de cada liga  
* puntos totales del usuario  
* resumen de puntos recientes

**Implicancias:**

* no existe top 100 global  
* no existe posición global  
* no existe ventana local global  
* la capa social vive en ligas

---

### **3.2 Modelo de scoring**

* scoring se ejecuta **solo post-partido**  
* no existe scoring en tiempo real continuo  
* scoring es:  
  * determinístico  
  * idempotente  
  * basado en eventos

**Flujo oficial:**

1. usuario predice  
2. kickoff bloquea predicción  
3. resultado oficial se ingesta  
4. scoring se ejecuta  
5. se actualizan puntos del usuario  
6. se recalculan standings de ligas afectadas  
7. se persiste snapshot final

---

### **3.3 Backend model**

El sistema sigue un modelo:

* **event-driven**  
* **batch-oriented**  
* **read-optimized (precomputado)**

**Principios obligatorios:**

* el frontend NO calcula lógica crítica  
* la API devuelve estados ya resueltos  
* rankings y acumulados se persisten (no se calculan on-demand)

---

### **3.4 Predicciones**

#### **Match-level**

* score obligatorio  
* en knockout:  
  * score de 90’  
  * clasificado solo si hay empate

#### **Macro**

* 1° y 2° por grupo  
* finalistas  
* campeón

#### **Ajuste post grupos**

* permitido una sola vez  
* solo si hubo picks iniciales  
* con penalización aplicada automáticamente

---

### **3.5 Deadlines**

* predicciones cierran en kickoff exacto  
* macro inicial cierra en kickoff del torneo  
* ajuste cierra en kickoff de octavos

No hay excepciones ni tolerancias.

---

### **3.6 Ligas**

* múltiples ligas por usuario  
* creación de liga simple dentro del plan operativo `free`  
* join por link o código  
* ranking completo dentro de cada liga  
* no hay roles avanzados en MVP
* límite operativo por liga en MVP: 20 jugadores

**Definición operativa del MVP:**

* `free`: hasta 20 jugadores

**Definición roadmap post-MVP ya documentada:**

* `plus`: 39 EUR, hasta 100 jugadores, sin branding premium  
* `business`: 79 EUR, hasta 300 jugadores, con nombre visible editable y logo custom

**Reglas operativas del MVP:**

* `memberLimit` puede exponerse como capacidad visible, pero su valor efectivo es `20`  
* una liga solo puede aceptar joins si está activa y no está llena  
* checkout, billing lifecycle, upgrades y branding premium quedan fuera del MVP operativo

---

### **3.7 UX principles obligatorios**

* home \= tablero de acción (no decorativa)  
* visibilidad permanente de estado:  
  * editable  
  * guardado  
  * bloqueado  
  * puntuado  
* un CTA principal por bloque  
* deadlines siempre visibles  
* mobile-first real  
* ads fuera del momento crítico

---

### **3.8 Monetización**

Permitido:

* banners inline

No permitido:

* interstitial antes de predecir  
* interrupciones en flujo de guardado

---

## **4\. Decisiones técnicas oficiales**

### **4.1 Arquitectura base**

* DB: Firestore  
* Backend: Cloud Run  
* Auth: Firebase Auth  
* Jobs: Cloud Scheduler \+ Cloud Run Jobs

---

### **4.2 API contract**

* REST JSON  
* `/api/v1`  
* camelCase en payloads  
* respuestas con envelope estándar:  
  * `{ ok: true, data }`  
  * `{ ok: false, error }`

---

### **4.3 Principios de datos**

* write optimized  
* read simple  
* denormalización controlada  
* snapshots persistidos  
* idempotencia obligatoria

---

## **8\. Definición de completitud del MVP**

El MVP está completo cuando:

* un usuario puede:  
  * registrarse  
  * predecir partidos  
  * guardar predicciones macro  
  * unirse/crear ligas  
  * ver puntos post-partido  
  * ver su posición en ligas  
* el sistema:  
  * bloquea correctamente por kickoff  
  * calcula scoring correctamente  
  * actualiza standings de ligas  
  * mantiene consistencia de datos

---

## **9\. Filosofía final**

**Mejor un sistema simple, consistente y confiable, que uno completo pero frágil.**

Este MVP está diseñado para:

* capturar usuarios rápido  
* generar retorno diario  
* escalar sin complejidad innecesaria

Todo lo demás es backlog.
