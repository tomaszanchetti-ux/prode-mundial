# Prode Mundial - Pre-Tournament UX Mode + Dynamic Standings Spec

## Documento 7

Especificación UX funcional para el período previo al inicio real del Mundial.

Este documento baja a producto implementable una nueva prioridad:

- generar engagement antes del primer partido
- aumentar completitud de predicciones de grupos
- introducir la idea de "Tu Mundial"
- preparar el loop diario real sin romper reglas ya cerradas

---

# 1. Propósito del documento

Este documento define cómo debe comportarse Prode Mundial durante el período pre-torneo.

Su objetivo es dejar cerradas:

- la lógica de activación del modo pre-torneo
- la nueva prioridad de `home`
- el flujo secuencial de predicción
- el concepto de progreso global de grupos
- la convivencia con el loop actual basado en próximo partido editable
- la transición natural hacia el modo torneo ya iniciado

Este documento NO cambia:

- deadlines por partido
- backend como source of truth
- scoring
- ligas como capa competitiva principal

---

# 2. Decisión de producto

Antes del primer partido del Mundial, la app NO debe comportarse como si ya existiera un loop diario real.

Durante ese período la UX principal debe ser:

- completar fase de grupos
- visualizar progreso
- construir el Mundial proyectado del usuario

La app debe sentirse más cercana a:

- onboarding jugable
- maratón de picks
- simulador personal del torneo

y menos cercana a:

- seguimiento diario de resultados
- puntos
- standings competitivos activos

---

# 3. Regla temporal del modo

## 3.1 Estado `preTournament`

El modo pre-torneo está activo:

- desde el lanzamiento / disponibilidad del producto
- hasta la apertura de la ventana del primer partido del torneo

Regla recomendada para MVP actual:

- usar el mismo criterio ya existente de apertura de predicción
- por lo tanto, el cambio ocurre cuando el primer partido entra en la ventana de predicción oficial

Con la configuración actual del proyecto:

- la transición práctica ocurre 5 horas antes del primer kickoff

## 3.2 Estado `liveTournament`

Una vez alcanzado ese trigger:

- la app vuelve a priorizar el loop ya vigente
- próximo partido editable
- quick prediction modal
- consumo diario

---

# 4. Prioridad UX obligatoria en pre-torneo

Durante `preTournament`, la `home` debe priorizar:

1. progreso global de fase de grupos
2. CTA principal `Seguir completando`
3. acceso a `Tu Mundial`
4. acceso a `Mundial Real` solo como espacio secundario si existiera

NO debe priorizar:

- puntos
- recent scoring
- ranking de ligas como bloque central
- auto-popup del próximo partido por default

---

# 5. Progreso global de grupos

## 5.1 Qué debe medirse

La experiencia debe comunicar claramente cuántos partidos de fase de grupos ya fueron predichos por el usuario.

Payload mínimo esperado:

- `completedMatches`
- `totalMatches`
- `remainingMatches`
- `completionPercentage`

Alcance MVP inicial de este feature:

- medir solo fase de grupos
- excluir knockout y macro picks de este progreso

## 5.2 UX esperada

Ejemplos:

- `0 / 48 partidos`
- `12 / 48 partidos`
- `48 / 48 partidos`

Microcopy sugerido:

- `Te faltan 36 partidos`
- `Vas 50%`
- `Ya completaste todos los grupos`

## 5.3 Estados visuales

- empty
- in progress
- complete

Color recomendado:

- empty -> neutral
- in progress -> primary
- complete -> success

---

# 6. Marathon Mode

## 6.1 Objetivo

Resolver la carga de predicciones de fase de grupos como flujo secuencial guiado.

El usuario debe poder:

- abrir el siguiente partido pendiente cronológico
- guardar
- avanzar automáticamente al siguiente
- mantener sensación de progreso continuo

## 6.2 Principios obligatorios

- cronología real del fixture como orden por default
- no bloquear navegación libre en otras pantallas
- no introducir reglas de edición nuevas
- no reemplazar el detalle de partido: convivir con él

## 6.3 Entry points

Debe poder abrirse desde:

- `home` pre-torneo
- `Tu Mundial` en estado vacío o parcial
- `matches` cuando existan muchos pendientes

CTA recomendados:

- `Seguir completando`
- `Continuar mis predicciones`
- `Completar fase de grupos`

## 6.4 Comportamiento del flujo

Cada paso debe mostrar:

- progreso global
- grupo
- posición dentro del flujo
- matchup
- kickoff
- score input
- CTA guardar
- salir / cerrar

Secuencia:

1. abrir siguiente pendiente cronológico
2. guardar
3. feedback visible
4. micro transición
5. abrir siguiente pendiente

## 6.5 Regla de edición posterior

Todo lo cargado en Marathon Mode sigue siendo editable luego:

- partido por partido
- hasta la apertura/cierre oficial que ya define backend

Marathon Mode acelera carga.
No redefine reglas del producto.

# 7. Tu Mundial

## 7.1 Objetivo

Mostrar cómo quedarían los grupos según las predicciones del usuario.

Debe responder una pregunta simple:

`¿Cómo va quedando el Mundial que yo pronostiqué?`

## 7.2 Alcance inicial recomendado

En la primera implementación:

- solo grupos
- sin bracket knockout proyectado
- sin comparativas complejas contra realidad
- sin explicar desempates avanzados en UI

## 7.3 Regla de backend

Aunque la vista sea muy UX-driven, la lógica derivada debe seguir el principio del proyecto:

- backend source of truth
- frontend sin lógica crítica pesada

Por lo tanto:

- la tabla proyectada no debe depender solo de cálculos ad-hoc en cliente
- debe existir read model o endpoint derivado estable desde backend

## 7.4 Contenido mínimo por grupo

- nombre del grupo
- estado de completitud del grupo
- tabla proyectada
- top 2 resaltados

Campos de tabla:

- equipo
- PJ
- PG
- PE
- PP
- GF
- GC
- DG
- Pts

## 7.5 Orden de equipos

Seguir criterio estándar:

1. puntos
2. diferencia de gol
3. goles a favor
4. siguientes criterios si hicieran falta

En MVP visual:

- mostrar orden resultante
- no sobre-explicar el desempate salvo necesidad

---

# 8. Transición a modo torneo

## 8.1 Trigger

La transición ocurre cuando existe un próximo partido dentro de la ventana de predicción activa.

Con la lógica actual del repo:

- 5 horas antes del kickoff del primer partido

## 8.2 Cambio esperado

A partir de ese momento:

- puede reactivarse el quick prediction modal actual
- la `home` deja de priorizar progreso global como bloque único dominante
- el producto pasa del modo preparación al modo partido-a-partido

## 8.3 Objetivo UX

El cambio debe sentirse natural, no abrupto.

Antes:

- completar
- proyectar
- prepararse

Después:

- predecir el próximo
- volver
- seguir resultados
- competir

# 12. Instrucción operativa para Codex

Implementar esta capa como evolución del front y de los read models existentes:

- sin romper contratos actuales
- sin mover lógica crítica a cliente
- priorizando UX de progreso y completitud

El objetivo no es solo "mostrar más datos".

El objetivo es:

- aumentar engagement pre-evento
- aumentar commitment psicológico
- preparar el hábito diario antes del primer partido
