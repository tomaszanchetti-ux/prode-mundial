# **Prode Mundial \- API Specification (Endpoints \+ Contracts \+ Payloads)**

**Versión:** v1  
**Objetivo:** definir con precisión la capa de contratos entre frontend, backend y admin para que Codex pueda implementar sin interpretar comportamientos implícitos.  
**Alcance:** API pública autenticada, API pública no autenticada, y API/admin mínima del MVP.  
**Alineación:** este documento asume el MVP **sin ranking global**, con foco en **mis ligas**, **mi posición dentro de cada liga**, **mis puntos**, **fixtures**, **predicciones match-level**, **predicciones macro**, y **ajuste post fase de grupos**. Esto corrige la tensión entre docs previos que aún mencionaban ranking global y el cambio de lógica costo-eficiente posterior.

---

# **1\. Propósito del documento**

Este documento define:

* endpoints exactos del MVP  
* request/response contracts  
* payloads JSON  
* reglas de auth por endpoint  
* errores esperados  
* convenciones de naming  
* reglas de locking y validación vistas desde API  
* shape de datos que el frontend puede asumir  
* separación entre lecturas de usuario, escrituras de usuario y operaciones admin

No redefine producto ni UX.  
Toma como fuente funcional:

* reglas cerradas del MVP  
* navegación y pantallas UX  
* modelo de datos y backend batch/idempotente  
* simplificación MVP sin ranking global

---

# **2\. Principios API obligatorios**

## **2.1 Frontend no calcula lógica crítica**

La API debe devolver estados ya interpretables:

* partido editable o no  
* predicción guardada o no  
* match puntuado o no  
* ajuste disponible o no  
* liga activa o no  
* posición del usuario en cada liga o no disponible

Esto es consistente con el principio de backend determinístico y read models simples.

## **2.2 Contratos estables y explícitos**

El frontend no debe inferir reglas desde campos ambiguos.  
Debe recibir banderas claras como:

* is\_editable  
* is\_locked  
* is\_scored  
* adjustment\_available  
* is\_member  
* can\_join

## **2.3 Lecturas optimizadas para pantalla**

Cada endpoint debe servir una necesidad UX concreta:

* home  
* fixtures list  
* match detail  
* macro picks  
* league detail  
* rankings by league  
* points summary

## **2.4 Escrituras idempotentes cuando aplique**

Guardar predicción o macro picks debe ser seguro ante retries de red.

## **2.5 Admin separado**

Endpoints admin no deben mezclarse con API cliente.

# **3\. Decisiones técnicas de contrato**

## **3.1 Estilo general**

* REST JSON sobre HTTPS  
* versionado por prefijo  
* timestamps en ISO 8601 UTC  
* frontend localiza hora para display si hace falta  
* auth con Firebase ID token en Authorization: Bearer \<token\>

## **3.2 Base path**

/api/v1

## **3.3 Content-Type**

Content-Type: application/json

## **3.4 Envelope de respuesta**

Para simplificar frontend, las respuestas exitosas usarán:

{  
  "ok": true,  
  "data": {}  
}

Errores:

{  
  "ok": false,  
  "error": {  
    "code": "MATCH\_LOCKED",  
    "message": "Este partido ya está bloqueado.",  
    "details": {}  
  }  
}

Los microcopys funcionales ya definidos en UX deben mapear contra estos errores.

---

# **4\. Convenciones globales**

## **4.1 Naming**

* snake\_case en backend interno  
* camelCase en payloads públicos de API

**Decisión recomendada:** usar **camelCase en API pública** para facilitar frontend web/app.

## **4.2 IDs**

Todos los IDs son strings opacas.

Ejemplos:

* userId  
* matchId  
* leagueId  
* teamId  
* groupId  
* predictionId

## **4.3 Paginación**

Para MVP, usar cursor simple solo donde haga falta:

* fixtures largos  
* rankings de ligas grandes

Pero la mayoría de endpoints pueden devolver payloads completos pequeños.

## **4.4 Nullability**

Cuando un valor aún no aplica, usar null, no strings especiales.

# **5\. Modelo de auth y permisos**

## **5.1 Público no autenticado**

Puede acceder a:

* landing config pública  
* preview de fixtures  
* reglas y puntos  
* preview limitada de ligas/invitaciones públicas si llega por token

## **5.2 Usuario autenticado**

Puede acceder a:

* home  
* profile  
* fixtures completos  
* match detail  
* guardar/editar predicciones  
* macro picks  
* ajuste post grupos  
* mis ligas  
* detalle de liga donde participa  
* crear liga  
* unirse a liga  
* mis puntos

## **5.3 Admin interno**

Puede acceder a:

* ingestar/corregir fixtures y resultados  
* disparar recálculos  
* bloquear/desbloquear  
* archivar ligas  
* ver jobs/logs mínimos

Esto respeta la matriz funcional de roles ya cerrada.

## **10.3 PUT /api/v1/matches/:matchId/prediction**

### **Objetivo**

Crear o sobrescribir predicción de un partido.

### **Regla**

* no hay endpoint “delete”  
* editar sobrescribe  
* si el partido está bloqueado, rechaza

Esto coincide con la recomendación UX de sobrescritura simple sin exponer borrar.

### **Request — fase de grupos**

{  
  "homeScorePred": 2,  
  "awayScorePred": 1  
}

### **Request — knockout con ganador en 90**

{  
  "homeScorePred": 2,  
  "awayScorePred": 1,  
  "predictedQualifierTeamId": null  
}

### **Request — knockout con empate**

{  
  "homeScorePred": 1,  
  "awayScorePred": 1,  
  "predictedQualifierTeamId": "ARG"  
}

### **Response**

{  
  "ok": true,  
  "data": {  
    "predictionId": "pred\_1",  
    "matchId": "m\_001",  
    "status": "saved\_editable",  
    "isEditable": true,  
    "homeScorePred": 1,  
    "awayScorePred": 1,  
    "predictedQualifierTeamId": "ARG",  
    "savedAt": "2026-06-20T12:10:00Z"  
  }  
}

### **Validaciones**

* scores enteros \>= 0  
* si knockout y empate predicho: predictedQualifierTeamId obligatorio  
* si no empate predicho: backend permite null  
* si now \>= kickoffAt: MATCH\_LOCKED

Estas validaciones están cerradas funcionalmente.

# **14\. Rankings**

## **14.1 Decisión API MVP**

**No habrá endpoint de ranking global en v1.**

### **Razón**

El documento de cambio de lógica elimina:

* ranking global  
* top 100  
* ventana local global  
* movimientos globales masivos

y deja solo:

* rankings internos por liga  
* mis puntos  
* mi posición dentro de cada liga

### **Implicancia**

Toda referencia a /rankings/global o similares queda fuera del MVP real aunque aparezca en docs anteriores.

## **14.2 Regla adicional de planes de liga**

Toda superficie de ligas del MVP debe exponer:

* `memberLimit`

`canJoin` debe resolverse en backend contemplando al menos:

* liga activa
* membresía no duplicada
* cupo disponible

Los planes pagos, billing y branding premium quedan post-MVP.

### **Reemplazo UX recomendado**

La tab “Rankings” debe consumir:

* GET /api/v1/leagues  
* GET /api/v1/leagues/:leagueId/standings

# **19\. Reglas de consistencia que el frontend puede asumir**

## **19.1 Match locking**

Si isLocked \= true, la API nunca debe aceptar escritura de predicción.

## **19.2 Knockout draw rule**

Si en knockout:

* homeScorePred \=== awayScorePred  
* entonces predictedQualifierTeamId es obligatorio

## **19.3 Macro champion rule**

champion debe pertenecer al array finalists

## **19.4 League standings**

La posición ya viene materializada o derivable sin recalcular client-side.

## **19.5 Scored predictions**

Si status \= scored, pointsAwarded no puede ser null

# **20\. Criterios de aceptación API**

## **20.1 Un frontend puede construir la home sin joins extra**

Debe bastar con GET /home.

## **20.2 Un frontend puede construir fixtures y detalle sin lógica oculta**

Debe bastar con GET /matches y GET /matches/:id.

## **20.3 Guardar predicción no requiere leer-escribir múltiples veces**

Debe bastar con un único PUT /matches/:matchId/prediction.

## **20.4 Toda pantalla social se sostiene con endpoints de ligas**

No debe existir dependencia de ranking global para cerrar UX del MVP.

## **20.5 Admin puede operar resultados y recálculos mínimos**

Sin panel complejo aún, pero con contratos claros.
