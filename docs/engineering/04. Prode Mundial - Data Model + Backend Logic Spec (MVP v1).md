# **Prode Mundial \- Data Model \+ Backend Logic Spec (MVP v1)**

---

# **1\. Propósito del documento**

Este documento define con precisión:

* modelo de datos completo (Firestore-oriented)  
* entidades, relaciones y estructuras  
* flujos backend obligatorios  
* lógica de scoring  
* lógica de rankings por liga  
* jobs batch y triggers  
* reglas de consistencia e idempotencia

👉 Es el documento base para que Codex pueda construir backend sin ambigüedad.

---

# **2\. Decisiones estructurales clave**

## **2.1 Arquitectura target**

* **DB:** Firestore (NoSQL)  
* **Backend:** Cloud Run (API \+ Jobs)  
* **Auth:** Firebase Auth  
* **Batch:** Cloud Scheduler \+ Jobs

## **2.2 Principios de diseño**

### **A. Write optimized \+ read simple**

* escribir datos procesados  
* evitar cálculos complejos en runtime

### **B. Event-driven (no realtime constante)**

* todo se recalcula en eventos:  
  * fin de partido  
  * cierre de fase  
  * ajustes

### **C. Idempotencia obligatoria**

* scoring puede ejecutarse múltiples veces sin romper datos

### **D. Denormalización controlada**

* rankings precomputados  
* acumulados persistidos

# **3\. Entidades principales**

---

## **3.1 Users**

users/{userId}

### **Campos**

{  
  user\_id: string  
  display\_name: string  
  email: string  
  country: string | null

  total\_points: number  
  macro\_points: number

  created\_at: timestamp  
  updated\_at: timestamp  
}

### **Notas**

* `total_points` \= acumulado total  
* `macro_points` \= desempate (grupos \+ finalistas \+ campeón)

# **5\. Flujos backend principales**

---

## **5.1 Lock de partido**

### **Trigger**

Cloud Scheduler (cada minuto)

### **Lógica**

if now \>= kickoff\_at:  
  set match locked  
  set predictions.is\_locked \= true

---

## **5.2 Ingesta de resultado**

### **Trigger**

* API externa o admin manual

### **Acción**

update match:  
  status \= finished  
  scores definidos

---

## **5.3 Scoring de partido (CRÍTICO)**

### **Trigger**

Cloud Run Job al detectar match finished

---

### **Flujo**

#### **1\. Obtener predicciones del partido**

predictions where match\_id \= X

#### **2\. Para cada predicción:**

Calcular:

* exact match  
* signo correcto  
* clasificado (si aplica)

#### **3\. Asignar puntos**

#### **4\. Update prediction**

points\_awarded  
is\_scored \= true

#### **5\. Update user aggregate**

users.total\_points \+= puntos

#### **6\. Update standings por liga**

Para cada liga donde participa el usuario:

league\_standings:  
  total\_points \+= puntos  
  exact\_hits++  
  correct\_signs++

---

## **5.4 Idempotencia**

Antes de correr scoring:

if match.is\_scored \== true:  
  EXIT

o validar contra `match_scoring_logs`

---

## **5.5 Rebuild manual (admin)**

Permitir:

recalculate\_match(matchId)

* borrar scoring previo  
* recalcular todo

# **6\. Ranking por liga (READ MODEL)**

---

## **6.1 Construcción**

NO se calcula en query.

Se mantiene actualizado en cada scoring.

---

## **6.2 Ordenamiento**

Ordenar por:

1. total\_points  
2. exact\_hits  
3. correct\_signs  
4. macro\_points  
5. timestamp

---

## **6.3 Query típica**

league\_standings/{leagueId}/table  
ORDER BY total\_points DESC  
LIMIT N

❌ joins  
❌ queries complejas

---

## **8.2 Usar**

✅ documentos precomputados  
✅ updates incrementales  
✅ batch processing

# **9\. Índices requeridos**

### **Firestore indexes**

* predictions by match\_id  
* league\_members by user\_id  
* standings by league\_id \+ total\_points

---

# **10\. Cost strategy**

---

## **Minimizar:**

* reads masivos  
* writes duplicados  
* recalculos innecesarios

---

## **Maximizar:**

* batch updates  
* documentos agregados  
* lecturas simples

---

# **11\. Seguridad**

---

## **Reglas base**

### **Users**

* solo editan su perfil

### **Predictions**

* solo owner puede escribir antes de lock

### **Standings**

* read-only desde frontend

### **Admin endpoints**

* protegidos

---

# **12\. Edge cases críticos**

---

## **Caso 1: partido corregido**

→ recalcular scoring completo

---

## **Caso 2: usuario sin predicción**

→ no crear documento innecesario

---

## **Caso 3: empate knockout sin clasificado**

→ invalidar predicción

---

## **Caso 4: doble ejecución de job**

→ idempotencia evita duplicación

---

# **13\. Resumen final (para Codex)**

---

### **El sistema funciona así:**

USER → guarda predicción

MATCH → llega kickoff → lock

MATCH → termina → resultado

JOB:  
  → calcula scoring  
  → actualiza users  
  → actualiza standings

FRONTEND:  
  → lee standings ya calculados

---

# **🚀 Conclusión**

Este diseño logra:

* simplicidad extrema  
* costo bajo  
* escalabilidad razonable  
* consistencia fuerte  
* cero lógica compleja en frontend  
* backend completamente determinístico
