# **Prode Mundial \- PROJECT STRUCTURE.md**

## **1\. Propósito del documento**

Este documento define la **estructura oficial del repositorio** de Prode Mundial.

Su objetivo es:

* evitar decisiones improvisadas de organización durante el desarrollo  
* establecer una base consistente para frontend, backend y shared contracts  
* definir dónde vive cada tipo de código  
* reducir ambigüedad para Codex al crear, editar o refactorizar archivos  
* permitir escalar el MVP sin degradar orden interno

Este documento es **binding** para toda implementación del MVP.

---

## **2\. Principios estructurales obligatorios**

### **2.1 Un solo repositorio**

El MVP debe construirse en **monorepo**.

Razón:

* frontend, backend, shared types, schemas y tooling deben evolucionar coordinadamente  
* reduce fricción para Codex  
* facilita consistencia de contratos  
* simplifica entornos, CI y handoffs

---

### **2.2 Separación clara por responsabilidad**

La estructura debe separar explícitamente:

* app web  
* API backend  
* jobs batch  
* admin tools mínimos  
* librerías compartidas  
* infraestructura/config  
* documentación  
* scripts operativos

No mezclar lógica de negocio crítica dentro de componentes UI.

---

### **2.3 Shared-first para contratos**

Todo contrato reutilizado entre frontend y backend debe vivir en `packages/shared`.

Incluye:

* tipos públicos  
* schemas de validación  
* enums de dominio  
* mappers API  
* constantes del juego  
* errores públicos

---

### **2.4 Dominio antes que capa, dentro de cada app**

Dentro de cada app, la estructura debe organizarse por **dominio funcional**, no por tipo técnico puro.

Ejemplo correcto:

* `matches`  
* `leagues`  
* `macro-picks`  
* `profile`

Ejemplo a evitar:

* `components`  
* `services`  
* `helpers`

Eso puede existir, pero subordinado al dominio.

---

### **2.5 Backend con core desacoplado**

La lógica crítica de negocio no debe quedar pegada a handlers HTTP.

Separar siempre:

* route / controller  
* service / use case  
* repository / db adapter  
* domain rules  
* mapper / serializer

---

### **2.6 Jobs como runtime separado**

Los procesos batch no deben mezclarse con API request handlers.

Los jobs deben tener entrada, ejecución y logging separados.

---

### **2.7 Tests cerca del código, pero tipados**

Cada módulo debe dejar claro:

* qué se testea a nivel unitario  
* qué se testea a nivel integración  
* qué se testea a nivel contrato

---

Dentro de cada dominio, usar subestructura consistente:

domains/matches/  
├── routes/  
├── controllers/  
├── use-cases/  
├── domain/  
├── repositories/  
├── mappers/  
├── schemas/  
├── policies/

### **Regla crítica**

* `routes/` define wiring HTTP  
* `controllers/` traduce request/response  
* `use-cases/` contiene la acción del sistema  
* `domain/` contiene reglas puras  
* `repositories/` encapsula acceso a DB  
* `schemas/` valida inputs/outputs  
* `mappers/` adapta datos internos a contratos externos

No saltear capas si el caso toca lógica de negocio relevante.

## **10\. Reglas de naming**

### **10.1 Archivos**

Usar kebab-case.

Ejemplos:

* `save-match-prediction.ts`  
* `league-standings-repository.ts`  
* `match-card.tsx`

### **10.2 Componentes React**

Nombre de export en PascalCase.  
Archivo en kebab-case.

Ejemplo:

* archivo: `match-prediction-form.tsx`  
* export: `MatchPredictionForm`

### **10.3 Tipos**

* tipos: PascalCase  
* enums: PascalCase  
* constants: UPPER\_SNAKE\_CASE cuando sean constantes globales

### **10.4 Variables**

camelCase.

### **10.5 Endpoints**

camelCase en payloads públicos; path REST estable.

---

## **11\. Reglas de imports**

### **Permitido**

* imports absolutos dentro de cada app si el tooling lo soporta  
* imports desde packages shared/config/ui/testing

### **No permitido**

* import cruzado directo entre `apps/web` y `apps/api`  
* importar internals privados de otro dominio  
* deep imports frágiles sin contrato estable

### **Regla**

Cada package/app debe exponer sus puntos públicos mediante `index.ts` o entrypoints controlados.

---

## **12.1 Tipos compartidos**

`packages/shared/src/types` o dentro del dominio correspondiente.

## **12.2 Contratos API**

`packages/shared/src/api/contracts`

## **12.3 Errores públicos**

`packages/shared/src/api/errors`

## **12.4 Constantes de scoring**

`packages/shared/src/constants`

## **12.5 Repositorios DB**

`apps/api/src/db/repositories` o `apps/jobs/src/db` según runtime

## **12.6 Lógica de standings**

* reglas puras: `packages/shared/src/domain/standings`  
* ejecución runtime: `apps/jobs` o `apps/api/use-cases` según corresponda

## **12.7 Seeds**

`scripts/data`

## **12.8 Mocks**

`packages/testing` o `tests/fixtures` cercanos al dominio

## **12.9 Analytics**

* eventos compartidos: `packages/shared/src/domain/analytics` si se crea  
* implementación cliente: `apps/web/src/lib/analytics`

## **12.10 Ads**

`apps/web/src/components/ads`

## **13\. Tests y estructura de testing**

## **13.1 Principio**

Cada dominio relevante debe tener tests en el nivel adecuado.

## **13.2 Niveles**

* unit: reglas puras  
* integration: repositorios, casos de uso, endpoints  
* contract: request/response  
* e2e: flows críticos

## **13.3 Ubicación**

Dos opciones válidas:

### **Opción A — cerca del código**

domains/matches/tests/

### **Opción B — carpeta `__tests__` local**

domains/matches/\_\_tests\_\_/

### **Regla**

Usar una sola convención y mantenerla en todo el repo.

## **15\. Manejo de variables de entorno**

### **Regla**

* nunca leer `process.env` arbitrariamente en cualquier archivo  
* centralizar acceso en módulos `config/`

### **Estructura recomendada**

Cada app define:

* `config/env.ts`  
* schema de validación  
* export de config parseada

### **No permitido**

* variables mágicas desperdigadas  
* fallback silencioso para valores críticos

---

## **16\. Lo que NO debe hacerse**

* no crear carpetas genéricas tipo `misc`, `stuff`, `helpers2`  
* no duplicar contratos API entre frontend y backend  
* no guardar tipos copy-pasteados en múltiples lugares  
* no mezclar lógica de scoring dentro de componentes de UI  
* no hacer import directo de DB desde componentes o hooks  
* no meter jobs dentro de endpoints HTTP  
* no crear una carpeta `utils/` gigante e indefinida con lógica de negocio  
* no agregar nuevos dominios sin reflejarlos en docs si cambian el mapa del sistema

---

## **20\. Regla final para Codex**

Cuando una task implique crear archivos nuevos:

1. primero ubicar el dominio correcto  
2. luego elegir la app/package correcto  
3. luego respetar naming y capas  
4. luego verificar si algo ya existe antes de duplicar  
5. luego dejar tests y exports consistentes

**La estructura no es decorativa. Es parte del sistema.**

Si una feature funciona pero rompe la arquitectura del repo, la task no está bien hecha.
